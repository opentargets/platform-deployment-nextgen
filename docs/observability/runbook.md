# Observability runbook

Commands for deploying the observability stack, checking that it is healthy, and diagnosing
problems.

See also [README.md](README.md) for how the stack is put together and
[gaps.md](gaps.md) for known issues.

## Deployment

The stack is deployed by ArgoCD, not by `helm install`. The Makefile targets below apply the
ArgoCD `Application` resource and then wait for the sync to complete. Both ArgoCD
Applications sync automatically from `main`, so a merge to `main` reaches the cluster without
running these.

### Deploy to devcluster

```bash
make deploy-observability-dev
```

Applies `argocd/devcluster-observability.yaml`, waits for the `observability` Application to
be created, waits for the operation to finish, syncs with `--prune`, then waits for the
Application to become healthy.

### Deploy to production

```bash
make deploy-observability-prod
```

The same sequence against `argocd/production-observability.yaml`.

Both targets run a `CLUSTER_CONTEXT_CHECK` guard (`Makefile:55-60`) that aborts if the
current `kubectl` context is not the expected environment, so you cannot accidentally apply to
the wrong cluster.

## Accessing the UIs

### Grafana

```bash
make port-forward-grafana
```

Prints the admin password from the `observability-grafana` Secret and port-forwards
`localhost:3000` to Grafana.

The password is generated by the chart, so it is not in version control. To read it
directly:

```bash
kubectl get secret -n observability observability-grafana \
  -o jsonpath="{.data.admin-password}" | base64 --decode
```

### Prometheus

```bash
make port-forward-prometheus
```

Port-forwards `localhost:9090` to the Prometheus server pod.

### ArgoCD

```bash
make port-forward-argocd
```

Prints the ArgoCD admin password and port-forwards `localhost:8080` to the ArgoCD server.

## Diagnostics

These are read-only and safe to run against either environment.

### Is everything running?

```bash
kubectl get pods -n observability
```

Expect: `observability-prometheus-server`, `observability-grafana`, `observability-loki`,
`observability-loki-gateway`, `observability-alloy` (one per node),
`observability-kube-state-metrics`, `observability-prometheus-node-exporter`,
`observability-prometheus-pushgateway`, `loki-canary`, and the two memcached cache
StatefulSets.

All should be `Running` or `Completed`. Check the node pool if pods are `Pending`:

```bash
kubectl get pods -n observability -o wide | grep Pending
kubectl describe node -l pool=ops
```

Pods stuck `Pending` on the `ops` pool usually mean the `workload=ops:NoSchedule` taint is
not being tolerated — check `nodeSelector` and `tolerations` in the profile file.

### Are logs being ingested?

Check that Alloy is running and has no errors:

```bash
kubectl logs -n observability -l app.kubernetes.io/name=alloy --tail=100
kubectl logs -n observability \
  -l app.kubernetes.io/name=loki,app.kubernetes.io/component=gateway --tail=100
```

Check Loki is accepting writes and serving queries:

```bash
kubectl logs -n observability \
  -l app.kubernetes.io/name=loki,app.kubernetes.io/component=single-binary --tail=100
```

Look for errors mentioning the GCS bucket — the Loki service account needs
`roles/storage.objectViewer` on the `open-targets-ops` bucket, and that binding is only
applied in the production project (`terraform/security.tf:127-133`).

### Are metrics being scraped?

List the scrape targets and their health:

```bash
kubectl port-forward -n observability \
  svc/observability-prometheus-server 9090:80
curl -s 'http://localhost:9090/api/v1/targets' | jq '.data.activeTargets[] | {job: .labels.job, health, lastError}'
```

Note the service listens on port `80` and forwards to the container's `9090`; the
port-forward above maps local `9090` to the service port.

A non-empty `lastError` points at the scrape job's problem. A job with zero targets means
its discovery found nothing.

### What labels are actually available?

The set of labels on a log stream or a metric series is the first thing to check when a query
returns nothing. The reference tables are in
[Logs labels](README.md#log-labels) and
[Metrics labels](README.md#metrics-labels).

For logs, confirm the labels on a real stream rather than guessing:

```bash
kubectl port-forward -n observability svc/observability-loki 3100:3100
curl -s -H 'X-Scope-OrgID: default' \
  'http://localhost:3100/loki/api/v1/labels' | jq
```

### Triage

| Symptom | Likely cause | Where to look | Gap |
|---|---|---|---|
| Grafana panel shows "Datasource not found" | Datasource uid mismatch — the panel references a uid the datasource does not have | `helm/observability/templates/secrets.yaml:21-28`; dashboard JSON | [G1](gaps.md) |
| Loki panels are empty, other panels work | The panel's stream selector does not match any label the pipeline sets. Use `{container="api"}` for API logs | [Logs labels](README.md#log-labels) | — |
| Log query returns nothing for a specific app | The app's container name is not the one in the selector. Check the `container` label value | `discovery.relabel` in the profile's Alloy config | — |
| Node logs and pod logs have different `cluster` values | devcluster uses two different values for the same label | `profiles/devcluster/observability.yaml` | [G6](gaps.md) |
| A change to `helm/observability/values.yaml` had no effect | ArgoCD passes the profile file, which overrides the base file | `profiles/*/observability.yaml` | [G5](gaps.md) |
| Prometheus target list full of connection errors, for the `kubernetes-services` job | The job targets a `blackbox` address that nothing serves | Prometheus targets API | [G4](gaps.md) |
| No alerts arrive | No alert rules exist, and Alertmanager is disabled | `prometheus.serverFiles`; `alertmanager.enabled` | [G2](gaps.md) |
| Loki cannot write to GCS | Missing or mis-scoped IAM binding on the chunks bucket | `terraform/security.tf:127-133`; the `loki-sa` annotation in the profile | — |
| Pods pending after a values change | Placement or toleration changed | profile file `nodeSelector` / `tolerations` | — |
| ArgoCD shows the Application out of sync | The cluster state drifted from Git | `argocd app get observability` | — |

## Validating a change

Before committing any change to the observability values:

```bash
helm lint helm/observability -f profiles/devcluster/observability.yaml
helm lint helm/observability -f profiles/production/observability.yaml

helm template observability helm/observability \
  -f profiles/production/observability.yaml --namespace observability
```

`helm template` renders the full manifest set. It is the fastest way to confirm a change
produced the resources you expected — for example that a new Service exists, or that a
`nodeSelector` is set.

The values files are validated against `helm/observability/values.schema.json`, which
enforces the allowed `relabel_configs` keys and `action` values. `helm lint` will fail on a
schema violation.
