# Observability runbook

Commands for deploying the observability stack, checking that it is healthy, and diagnosing
problems.

See also [README.md](README.md) for how the stack is put together and
[gaps.md](gaps.md) for known issues.

## Deployment

The stack is deployed by ArgoCD, not by `helm install`. The Makefile targets below apply the
ArgoCD `Application` resource and then wait for the sync to complete. Both ArgoCD
Applications sync automatically from `main`, so a merge to `main` reaches the cluster without
running these.

### Deploy to devcluster

```bash
make deploy-observability-dev
```

Applies `argocd/devcluster-observability.yaml`, waits for the `observability` Application to
be created, waits for the operation to finish, syncs with `--prune`, then waits for the
Application to become healthy.

### Deploy to production

```bash
make deploy-observability-prod
```

The same sequence against `argocd/production-observability.yaml`.

Both targets run a `CLUSTER_CONTEXT_CHECK` guard (`Makefile:55-60`) that aborts if the
current `kubectl` context is not the expected environment, so you cannot accidentally apply to
the wrong cluster.

## Accessing the UIs

### Grafana

```bash
make port-forward-grafana
```

Prints the admin password from the `observability-grafana` Secret and port-forwards
`localhost:3000` to Grafana.

The password is generated by the chart. When you run the `port-forward-grafana` this will optput the password.

```bash
echo "Grafana admin password:"
Grafana admin password:
<password>
```

To read the password at any given point run:

```bash
kubectl get secret -n observability observability-grafana \
  -o jsonpath="{.data.admin-password}" | base64 --decode
```

### Prometheus

```bash
make port-forward-prometheus
```

Port-forwards `localhost:9090` to the Prometheus server pod.

## Diagnostics

These are read-only and safe to run against either environment.

### Is everything running?

```bash
kubectl get deploy -n observability
```

Expect: `observability-prometheus-server-*`, `observability-grafana-*`, `observability-loki-*`,
`observability-loki-gateway-*`, `observability-alloy-*` (one per node),
`observability-kube-state-metrics-*`, `observability-prometheus-node-exporter-*` (one per node),
`observability-prometheus-pushgateway-*`, `loki-canary-*`, and the two memcached cache
StatefulSets.

All should be `Running` or `Completed`. Check the node pool if pods are `Pending`:

```bash
kubectl get pods -n observability -o wide | grep Pending
```

Pods stuck `Pending` on the `ops` pool usually mean the `workload=ops:NoSchedule` taint is
not being tolerated — check `nodeSelector` and `tolerations` in the profile file.

### Are logs being ingested?

Check that Alloy is running and has no errors:

```bash
kubectl logs -n observability -l app.kubernetes.io/name=alloy --tail=100
kubectl logs -n observability \
  -l app.kubernetes.io/name=loki,app.kubernetes.io/component=gateway --tail=100
```

Check Loki is accepting writes and serving queries:

```bash
kubectl logs -n observability \
  -l app.kubernetes.io/name=loki,app.kubernetes.io/component=single-binary --tail=100
```

Look for errors mentioning the GCS bucket — the Loki service account needs
`roles/storage.objectViewer` on the `open-targets-ops` bucket, and that binding is only
applied in the production project (`terraform/security.tf:127-133`).

### Are metrics being scraped?

List the scrape targets and their health:

```bash
kubectl port-forward -n observability \
  svc/observability-prometheus-server 9090:80
curl -s 'http://localhost:9090/api/v1/targets' | jq '.data.activeTargets[] | {job: .labels.job, health, lastError}'
```

A non-empty `lastError` points at the scrape job's problem. A job with zero targets means
its discovery found nothing.
